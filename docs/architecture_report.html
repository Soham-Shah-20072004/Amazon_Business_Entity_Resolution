4 · Stage by stage, with settings

Stage 0 · Prepare

doneer/text.py · er/prepare.py · scripts/prepare_data.py

Reads each TSV in 400k-row chunks (C engine, QUOTE_NONE so a stray quote cannot swallow rows), normalises in parallel on all cores, and appends to one parquet file per split. About 15 minutes per split on 4 CPUs; reused by every later run.

  • norm: NFKC, lowercase, &→and, punctuation → space; combining marks kept (dropping them split every Devanagari word into letters – a bug we found and fixed).
  • ascii: unidecode (Hindi/Gujarati → Latin, French accents dropped), with a fix for candra-O (ऑ) and digit/letter splitting (12a → 12 a).
  • canon: separate maps for names (pvt→private, ltd→limited, corp→corporation …) and addresses (rd→road, bd→boulevard, US + Indian state names → codes, Bombay→Mumbai, Gurgaon→Gurugram, unidecoded Hindi state names → codes).
  • core name: canon name without legal tokens; acronym of core; skeleton: sound frame (drop inner vowels and h, collapse doubles, ph→f, nb→mb) so Delhi / दिल्ली → dl, Gujarat / गुजरात → gjrt, Smart Management Private Limited and its Gujarati form differ by one letter.
  • numbers (leading zeros stripped: J-03/79 = J-3/79) and postcode-like tokens (5–6 digits, joins Indian “560 001”).

Stage 1 · Blocking (candidate generation)

doneer/retrieval.py

Runs independently for every country and for each target source (S2, S3), so neither source crowds out the other. The union of five blockers forms the candidate list.

BlockerHow it worksCurrent settings
ann_fullChar n-gram TF-IDF of “canon name | canon address” → truncated SVD (LSA) → L2-normalised vectors → FAISS IVF-Flat, inner productchar_wb 3–4, 262k features, sublinear tf, 128 dims (float16 on disk), nlist = 2√n, nprobe 32, top 25
ann_addrSame on the canon address alonechar_wb 3–4, top 25
ann_skelSame on “name skeleton | address skeleton”; bridges scripts and vowel typoschar_wb 2–4, top 25
rareName / address / postcode tokens hashed into 224 columns; a token is “rare” if it appears in few pool records; score = sum of IDF of shared rare tokens (a sparse matrix product)rare = df ≤ max(100, 300 per million pool records) → ~900 in a 3M pool; top 20
exactIdentical core name within the countryblocks with more than 50 pool records skipped (generic names)

Every candidate pair then gets all three cosines and the rare score, even from views that did not retrieve it. A reverse check searches, for each candidate record, its top 3 S1s among all S1s of the country (full view). Features: is this S1 the best / second best for the candidate, gap to the best, margin between the best two. This encodes the one-owner fact and is computed identically on train (sampled queries) and test.

Name-only search was replaced by the combined “full” view after the real-data smoke test (name-only found 47% of matches alone on the full pool, with few unique finds). The 93.4% recall figure comes from the older settings (name / addr / skel, k = 15, fixed rare threshold); the current settings have not been measured on the full train pool yet.

Stage 2 · Pre-ranker

donescripts/run_stage_b.py · er/features.py
  • Input: every blocked pair (~164 per S1). Features (24, cheap): blocker flags, number of blockers, source, three cosines, rare score, rank and gap-to-best of each score within the S1's list per source, list size, reverse-check features.
  • Model: LightGBM binary, learning rate 0.1, 63 leaves, min 50 per leaf, 90% features and 80% rows per tree, early stopping 50. Trained on all positives + 30% of negatives; 3-fold grouped out-of-fold scores.
  • Cut: keep top-k per S1 with p ≥ t; (k, t) chosen as the smallest list within a 0.5% loss budget of the positives blocking found. The full run chose a generous cut: ~18 per S1.

Stage 3 · Matcher

doneer/features.py · er/model.py
  • Features (~80): the cheap set plus rapidfuzz ratio / partial / token-sort / token-set / Jaro-Winkler on names, core names and skeletons; address ratio / partial / token-set / token-sort; exact flags; lengths; IDF-weighted token overlap, max shared and max unshared IDF for names and addresses (sparse matrix ops); number count, Jaccard, overlap, conflict, subset, dropped-digit prefix, first-number agree / conflict; postcode agree / conflict / missing; legal-suffix mismatch; acronym; name inside the other's address; rank / gap of name and address similarity within the list.
  • Model: LightGBM binary (log loss, second-order gradient boosting), learning rate 0.05, 127 leaves, min 40 per leaf, 80% features and rows per tree, L2 = 1, early stopping 100. 5-fold out-of-fold scores grouped by S1; final model on all pairs with 1.1 × the mean best iteration count.
  • Training data: 60,000 random train S1s searched against the full pool; label = ground truth. Negatives are the blocker's own wrong candidates (hard negatives by construction).
  • Strongest features (gain, smoke run): address skeleton token-set, core-name ratio, number Jaccard, name partial ratio, Jaro-Winkler, number subset, first-number conflict, rare score.

Stage 4 · Decision

doneer/evaluate.py
  • Keep a pair when p ≥ t; thresholds 0.05–0.95 swept (per-source thresholds optional), with and without the one-owner rule, choosing whatever maximises the exact macro F0.5 on out-of-fold scores.
  • One owner: if several S1s claim the same record, only the highest-probability S1 keeps it.
  • No forced match: an S1 with nothing above t gets an empty list (worth 1.0 when it is a true singleton).

Stage 5 · Focus set, cross-encoder and stacking

ready to runscripts/gpu/cross_encoder.py · scripts/run_combine.py
  • Focus set: pairs with first-stage matcher p ≥ 0.01, top 8 per S1, identical rule on train (out-of-fold p) and test. Pairs below 1% are never predicted anyway, so this costs essentially no recall; it cuts candidate_pairs.tsv from ~18 to ~5–7 per S1 and bounds GPU time.
  • Cross-encoder: sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2 (Apache-2.0, 118M parameters, 12 layers × 384 hidden, 250k-piece SentencePiece vocabulary, 50+ languages incl. Hindi, Gujarati, Marathi, French). Input [CLS] name | address [SEP] name | address [SEP] in the original script, max 96 tokens; new 1-logit head; binary cross-entropy; AdamW lr 3e-5, weight decay 0.01, 6% linear warm-up; 2 epochs; fp16; both T4s via DataParallel; length-bucketed batches.
  • Out-of-fold for stacking: 2 folds by S1; each half is scored by the model trained on the other half; test gets the average of both.
  • Stacked matcher: the Stage 3 feature set + cross-encoder score, its rank and gap in the list; same LightGBM recipe and decision tuning; prints the Stage 3 and stacked out-of-fold F0.5 side by side before writing files.

5 · How we validate

  • Query sampling, full pool: training and blocking reports use random train S1s, but always search the complete S2/S3 pool, so the look-alike density matches test.
  • Grouped folds: fold = hash(S1 row) mod k; all candidates of one S1 share a fold, so every S1 is scored by a model that never saw it.
  • Exact metric: macro F0.5 per S1 including singletons (empty prediction = 1.0), vectorised so thresholds can be swept hundreds of times.
  • Recall accounting: true pairs lost in blocking or in the pre-ranker count as misses in the metric; the report prints union recall, kept recall and final recall separately.
  • Slices with points lost: points lost = Σ(1 − F0.5) over the slice / N × 100, i.e. how many leaderboard points each group costs. Slices: singleton, 1, 2–3, 4+ matches, cross-script match, blocking missed, pre-ranker dropped, same-name distractor, S1 address without numbers, per country.
Caveats: the estimate comes from a 60k-S1 sample (≈ 2.7% of train); test is India-heavy and contains France, which we cannot validate locally; the one-owner competition inside a sample is weaker than on the full test set. Compare the out-of-fold score with the public leaderboard before trusting small gains.

7 · Compute, runtime and caching

All runs so far are Kaggle notebooks: 4 CPU cores, 31 GB RAM, 12 h limit, "Save & Run All" so they survive disconnects. AWS: SageMaker quotas are 0 on the account; an EC2 16-vCPU request (Hyderabad) is pending.

What is cached now

Stage B saves the matcher's train pairs (features, labels, out-of-fold p), all kept test pairs with features, the sampled S1 list and their truth. Matcher, threshold, stacking and cross-encoder changes reuse them: ~10 min (CPU) or ~1 h (with the GPU cross-encoder) instead of 8 h.

Speed-ups in the code

Multi-threaded cosine scores (7× on that step) and Polars group ranks (2×), both measured above. GPU nearest-neighbour search (faiss-gpu on a T4 notebook; expected 1 h 50 m → 10–15 min, untested on GPU yet). NPROBE knob. The focus set limits the expensive stages to ≤ 8 pairs per S1.

Why Polars is not a rewrite

pandas was only the slow part in the group ranks. The rest of the time goes to numeric work that already runs in C/C++ (FAISS, sparse products, LightGBM, rapidfuzz) or to Python text vectorisation. A full pandas → Polars port would change little and risk bugs before the deadline.

Still expensive

Any change to blocking or the pre-ranker needs the long run (now an estimated ~5–6 h on CPU; less with GPU search). Next levers: run Stage B on a GPU notebook, a tighter pre-ranker cut (fewer rapidfuzz pairs), skip cross-view cosines, or split test by country across parallel notebooks.

9 · Open research directions

Ordered roughly by expected gain per hour. Each can be researched independently; measured changes go through the out-of-fold report first.

Multi-match completion via S2/S3 duplicates

biggest sliceCPU

48% of S1 have 4+ matches and lose 1.76 points. If record a is a confident match and record b is a near-duplicate of a within S2/S3, b is likely a match too. Idea: similarity between candidates of the same S1 as features (max similarity to the S1's confident matches), or a second pass adding siblings of accepted pairs. Must be precision-safe.

Blocking recall

highlong rerun

Measure the current settings on the full pool first. Then: fine-tuned bi-encoder (contrastive, in-batch + hard negatives) as a fourth view; better transliteration for Indic names (e.g. an Indic transliteration library for a second Latin form); per-view k; nprobe 48–64 on GPU; sorted-neighbourhood on the skeleton key.

Cross-encoder choices

mediumGPU

MiniLM first. Candidates: MuRIL (Apache-2.0, trained on Indian languages including transliterated text – best fit for the cross-script slice), multilingual-e5-small (MIT), XLM-R base (MIT). Also try one epoch vs two, and field markers (name: / address:).

Address structure

mediumCPU

Parse house / unit / street / locality / city / state / PIN heuristically and compare component by component (conflict vs missing). Landmark phrases (“near SBI ATM”) as weak evidence. Helps same-name distractors (e.g. same chain, different branch).

Decision rules

cheapCPU

Per-source and per-country thresholds (already supported: --per-source); entity-level logic such as a lower threshold for siblings when the top candidate is very strong; calibration check of p by slice.

Pre-ranker and candidate size

cheaplong rerun

Add 2–3 cheap string features (e.g. token-set on core names) to the pre-ranker; tune the loss budget against the final metric; report the recall-vs-size curve for the write-up, since smaller candidate sets rank higher.

Validation stress tests

cheap

Train on US only and evaluate on India (unseen-country proxy for France); look at the hardest false positives and false negatives by hand for label noise and missing rules.

11 · Glossary

Blocking
Cheaply picking a short candidate list per S1 so we never compare all pairs. Its recall is the ceiling for everything after it.
LSA vector
TF-IDF of character n-grams compressed to 128 numbers with truncated SVD; similar strings get similar vectors.
FAISS IVF
An index that groups vectors into cells; a search only scans the few cells nearest the query (nprobe of nlist).
Rare-word index
Word → records containing it, used only for words that appear in few records; shared rare words are strong evidence.
Pre-ranker
Fast first model that trims ~164 blocked candidates to the plausible ones.
Matcher
Main LightGBM model that outputs P(same business) for a pair.
Out-of-fold (OOF)
Scores for training S1s produced by models that did not see those S1s; used to tune thresholds and to estimate the score honestly.
One owner
No S2/S3 record belongs to two S1s, so if several S1s claim it, only the best keeps it.
Focus set
Pairs with first-stage p ≥ 0.01, top 8 per S1; the input of the final model and our candidate_pairs.tsv.
Cross-encoder
A transformer that reads both records together and scores the pair; more accurate than comparing separate vectors, but only affordable on a few pairs per S1.
Stacking
Feeding one model's score (the cross-encoder) as a feature into another (LightGBM).
Points lost
How many leaderboard points (out of 100) a slice of S1s costs: Σ(1 − F0.5) over the slice / N × 100.
